# Main Responsibility: Product notes beyond the current MVP scope.
#
# Capture future requirements and design questions so post-MVP work
# stays intentional and happens on a separate branch.

1. Work beyond the MVP must happen on a separate branch.
2. MVP covers cash-receipt processing; PDF bank statements may be possible later
   but that must be verified. Card payments without a cash receipt also need a path.
3. Untracked spending must be coverable somehow — spending without a receipt,
   nightlife, tips, lending money, and similar. Every kind of spend should be
   recordable in some form.
4. The user must be able to create an expense that cannot be backed by a document
   (tip, lost/missing cash receipt, nightlife, cash lost from a pocket, etc.).
   The approach needs design thought: today an expense is tied to a document
   (document_id NOT NULL / unique), and extractions are document-scoped. Options
   include nullable document_id, a separate table, a new UI page, a new object,
   or a special case of an existing type.
5. Essentially all of a user's spending must be capturable — ~50% coverage
   loses the product's meaning. Target at least ~98%. The user may still skip
   an entry, but the product must allow recording it; ideally capture becomes
   as automatic as possible later.
6. Later, AI access to medians, averages, and stats could guide spending, e.g.
   "you are spending 10 percent more money in the last 7 days for food,
   compared to last month, consider ....."
7. Each purchased line item may need its own category for detailed spend analysis
   (needs further design).
8. Far future: advice questions such as whether to buy something given balance,
   recent spending, and time until payday; also personal fixed obligations
   (loans, subscriptions, mandatory payments) for better analysis and guidance.
9. The system must ensure that no identical documents get inserted in the DB,
   it can be denied early in UI. Two same documents must not exist because the
   probability of wrong calculations and duplicated data rises. This may happen when
   OCR scanning - it detects some number and checks if there is such document in DB.
10. Pending-documents inbox (non-SAVED docs): useful after unfinished review,
    PROCESSING_FAILED, or expense unapprove (document back to REVIEW_REQUIRED,
    file kept). Lets the user resume approve or permanently delete the document
    + file from that section. It does not replace re-upload — a new upload still
    creates a new document; the inbox only surfaces work that already exists.
    Planned as a separate sub-task alongside Flow C (not a substitute for the
    expense list). Forever wipe from the expense screen can stay out of MVP if
    unapprove + pending delete covers the need.
    After unapprove: stay on / return to #/expenses (so the row disappearing is
    visible). Show a short message that the document is in the pending inbox,
    with a link to #/documents — do not force-redirect to the inbox. An inbox
    badge/counter can come later.
11. Beyond expenses: income tracking (form TBD); a Saved/savings area,
    possibly split by categories; investments as a later idea; loan/credit
    instalments (low priority / unlikely).
